# 0007 Apple Passwords holds live logins and passkeys. devPassword is the system of record.

Date: 11 October 2026. Status: accepted by Nino. Record type: lite (Personal). Closes the reuse check owed before Stage 2.

- **Decision.** Apple Passwords is the system of engagement for logins and passkeys: create, change, AutoFill and sign-in with Face ID or Touch ID happen there. devPassword is the system of record: the master for every non-login record, and the complete, encrypted, independent record of everything, including a dated history of logins. Logins flow one way, Apple to devPassword. Nothing is ever written back to Apple after the one-off migration.
- **Why.** Apple gives no API to read or write Apple Passwords. Two editable stores with no change feed is a sync engine with no way to see changes. In practice, password changes happen in the browser and land in Apple anyway. The only way for devPassword to be the true master for logins is to be the AutoFill provider itself. That is the spec's riskiest assumption, the largest attack surface, and it means building passkey support. Nino increasingly wants passkeys with biometrics, which Apple already does. Apple Passwords does not cover cards, ID documents, prescriptions, vehicles, insurance or expiry dates, so that is where devPassword earns its place.
- **Rules.**
  - One master per field, and each login has exactly one master. Default: Apple. Everything that is not a login lives in devPassword.
  - Apple-mastered logins appear in devPassword as a read-only snapshot. They show the snapshot date. They cannot be edited. Their passwords can be viewed and used with "Pick characters".
  - devPassword-mastered logins (amended 11 October 2026): for sites Apple AutoFill cannot fill, such as banks that ask for each character in a separate box. Full, editable logins that live only in devPassword and are never put into Apple. Nino declines Safari's offer to save them. If one appears in an Apple import, devPassword flags it as a duplicate master and Nino chooses which side wins.
  - Banking logins taken from the snapshot are flagged when the snapshot is older than the refresh limit, because "Pick characters" on a stale password gives wrong characters.
  - Each import is compared with the previous one and records new, changed and removed logins with dates. This history is something Apple does not keep.
  - The vault shows the age of the login snapshot and asks for a refresh past a limit Nino sets (proposed 30 days).
  - Records link to a login by website and username, never by copying the password.
  - Passkeys: devPassword never holds passkey private keys, even if an export offers them. The snapshot records only that a passkey exists (website, username, date seen).
  - Plaintext handling: preferred import is credential exchange (macOS 26 / iOS 26), with no file on disk. Fallback: devPassword watches for the exported CSV, imports it at once and deletes it, then confirms it is gone. A plaintext CSV is never kept, backed up or opened in an AI session (N1).
- **Second secrets (amended 11 October 2026).** Some UK bank logins ask for a password and then selected characters (for example 2, 5 and 7) from a second password or memorable word. Apple Passwords cannot do this. Rule: the first password stays in Apple, so AutoFill works. The second secret lives only in devPassword, on the bank's record, and is never put in an Apple Passwords note, because the snapshot would then copy it. Splitting the two is a security gain: a compromise of either store alone does not open the account. Any secret field in devPassword gets "Pick characters": Nino types the positions asked for, and devPassword shows only those characters, labelled by position, large, hidden again after a short time. It never copies them to the clipboard. The whole secret is shown only on a deliberate reveal, which is logged in Activity like other reveals.
- **Migration (one-off, the only write to Apple).** Logins now in devPassword (from mSecure) and in LastPass go into Apple Passwords by CSV import on the Mac. Check counts. Delete the CSVs. Then the first snapshot import brings them back into devPassword as read-only entries. Retire LastPass after a check period.
- **What this removes.** The browser AutoFill provider, the sandbox and App Group migration (decision 0002 stands), the password generator, editing of Apple-mastered logins, and CloudKit sync of logins. The Stage 0 AutoFill proof is no longer needed.
- **What it changes for the iPhone.** The iPhone app becomes a records app, not a password manager. First version: read-only, opening the latest encrypted backup with Face ID. Edit and sync only if read-only proves a real limit.
- **Accepted risks.**
  - The login snapshot is only as fresh as the last import.
  - Logins and passkeys depend on Nino's Apple account. Independence comes from a second way in, not from copying keys: Apple account recovery contact, Legacy Contact, and a second authenticator on critical accounts. See open items.
- **Test that decides the import route.** Half a day: can devPassword receive logins from Passwords on macOS 26 through credential exchange without becoming a full browser AutoFill provider? Record the answer here.
- **Reversal point.** If Apple publishes a read API for Passwords, or if Nino leaves the Apple platform.
